# CodeRules — правила кода и архитектуры

> Живой документ: сюда записываются договорённости по стилю, архитектуре и подходам к разработке.  
> **Обновлять**, когда появляются новые договорённости или меняется принцип в проекте.

**Последнее обновление:** 2026-10-06

Комментарии и имена в коде — на английском.

---

## 1. Общие принципы

- **Минимальный scope** — только то, что нужно сейчас; без «на будущее» в коде, если фича ещё не нужна.
- **Без over-engineering** — не плодить абстракции ради одной строки; не дублировать состояние.
- **Комментарии** — только для неочевидной логики или технических нюансов; код в основном самодокументируемый.
- **Язык комментариев** — **только английский** (`/// <summary>`, `//`, `[Tooltip]`; `#region` не используем). См. §1.1.
- **Тесты** — добавлять по запросу или когда дают реальную пользу, не «ради галочки».
- **Сцена — источник правды для вида.** В рантайме не меняем свойства объектов (выравнивание, размер шрифта, цвет, layout и т.п.), если без этого нельзя обойтись. См. §7.

### 1.1. Язык комментариев в коде

Все комментарии в скриптах проекта, включая редакторские, — **на английском**:

| Что | Правило |
|-----|---------|
| `/// <summary>` на типах, методах, полях | English |
| `//` и `/* */` inline / block | English |
| `[Tooltip("...")]` на `[SerializeField]` и публичных полях | English |
| `Debug.Log*` сообщения для разработчика | English |

❌ `/// Заезд от запуска до остановки.`  
✅ `/// One run, from the launch to the stop.`

Старый неанглийский текст в комментариях переводим **при касании файла**, не массовым рефакторингом без задачи.

## 2. Архитектура: логика отдельно от представления

### Решение

**Core** — обычные C#-классы без Unity UI: правила игры, расчёты, состояние.  
**Data** — то, что сохраняется, и репозиторий, который это читает и пишет.  
**View / UI** — `MonoBehaviour`-ы сцены: экраны, HUD, визуал, звук.  
Между ними — один composition root, не «логика игры внутри кнопок».

```
[ View / UI ]  ←→  [ Composition root ]  ←→  [ Core + Data ]
  экраны, HUD,       создаёт зависимости,       правила, расчёты,
  визуал, звук       подписывает один раз       сохранение
```

### Почему

- Правила и расчёты не зависят от Canvas и их можно читать и проверять отдельно.
- Экраны не знают про формат сохранения и не считают игровую логику сами.
- Composition root один: он создаёт зависимости, передаёт ссылки и подписывает объекты друг на друга один раз при старте.

### Не делать

- Создавать иерархию UI в **рантайме** (`new GameObject`, `AddComponent` для экранов, `EventSystem`, Canvas). Иерархия живёт в сцене и правится в редакторе. Недостающая ссылка — `Debug.LogError`, не скрипт, который «допишет» сцену.
- Искать `[SerializeField]` через `Find*` / `GetComponent` как fallback.
- Тащить Unity UI в Core (`Button`, `Text` в расчётах).
- Делать `static Instance` / god-service: поток идёт через composition root и переданные ссылки.

## 3. Слои и ответственность

| Слой | Ответственность |
|------|-----------------|
| **Core** | Правила, расчёты, состояние. Без UI. |
| **Data** | Сохраняемые данные и репозиторий. |
| **View / UI** | Объекты сцены: экраны, визуал, звук, ввод. |

Один публичный тип на файл — предпочтительно. Допустимо держать рядом тесно связанные вещи в одном файле (например, `enum` и класс, который его использует), не растаскивать «на будущее».

### Поток

Composition root подписывает объекты один раз при старте. Дальше объекты общаются через события и переданные ссылки.

Не резолвить зависимости на каждый клик: ссылка кэшируется при подписке.

### Звук

Источники звука и клипы — в инспекторе, не создаются в рантайме. Игровой код не вызывает `AudioSource` напрямую из разных мест: он поднимает событие, а звук играет один слушатель.

- Не плодить mixer / AudioMixer groups, пока нет раздельных шин.
- Не искать `AudioListener` / `AudioSource` через `Find*`.

## 4. Данные и сохранение

### Принцип

UI **не считает** статистику и **не пишет** сохранение сам. Он показывает готовые значения и сообщает о действиях игрока.

### Слои данных

| Часть | Ответственность |
|-------|-----------------|
| **Record** | Только поля, которые сохраняются. |
| **Repository** | Загрузка и сохранение, без правил игры. |
| **Rules** | Формулы и правила, без I/O. |

❌ Плохо — всё в одном static-классе: кэш + сохранение + правила + UI-строки.  
✅ Хорошо — запись тупая, репозиторий только читает и пишет, правила считают, composition root решает, *когда* сохранять.

## 5. Именование

### Поля и переменные

- **Полные, понятные имена** — без сокращений и «обрезков».
  - ✅ `repository`, `difficulty`, `deltaTime`, `position`
  - ❌ `repo`, `diff`, `dt`, `pos`, однобуквенные `q` / `s` вместо смысла
- Имя должно сразу читаться: по переменной понятно, **что** это.

### Классы

- **Не использовать `sealed`** на классах проекта — модификатор избыточен (нет иерархии, которую нужно закрывать).
  - ✅ `public class RunScore`
  - ❌ `public sealed class RunScore`

## 6. Стиль кода (форматирование)

### Порядок членов в классе

Сверху вниз:

1. **Вложенные типы** (`enum`, `struct`, `class`).
2. **`const`** и **статические поля** (`static`, `static readonly`).
3. **Публичные события**.
4. **Поля экземпляра** — сначала `[SerializeField] private`, затем остальные `private` instance fields.
5. **Публичные свойства** (включая `public static` properties).
6. **Методы** — в таком порядке:
   - **`OnEnable` / `OnDisable`** — если есть, всегда **первые** методы в классе; идут **подряд парой**, между ними ничего не вставляем. Если есть только один из пары — он всё равно первый.
   - Остальные Unity runtime callbacks: `Awake`, `Start`, `Update`, `FixedUpdate`, `LateUpdate`, `OnDestroy` и аналоги (`OnCollisionEnter`, `OnPopulateMesh`, …).
   - Публичные инициализационные методы (`Subscribe…`, `Begin`, `Show…`, …). **Не** использовать `Bind` / `Unbind` в именах методов. Подписка: `Subscribe` / `Unsubscribe`. Показ данных: `ShowRecord`, `SetText`. Очистка: `Clear` / `Release` / `Dispose`.
   - Остальные `public` методы.
   - `protected` методы.
   - `private` методы.
   - Unity editor callbacks: `OnValidate`, `Reset`, `OnDrawGizmos` и аналоги.

Конструктор — вместе с методами, после свойств.

`#region` для группировки **не используем** — порядок сам задаёт структуру.

### Модификаторы доступа

**Всегда писать модификатор явно** (`public` / `private` / `protected` / `internal`). Не полагаться на default C# (`private` у членов типа, `internal` у top-level types, `public` у членов интерфейса).

Относится ко **всем** объявлениям, у которых модификатор допустим:

- типы: `class`, `struct`, `enum`, `interface`, вложенные типы;
- поля, `const`, события;
- свойства, индексаторы, методы, конструкторы;
- члены интерфейса (`public void Restart();`).

Не относится к локальным переменным, параметрам методов и лямбд — у них модификатора нет.

❌ Плохо:

```csharp
[SerializeField] Button playButton;
readonly List<Coin> _coins;
void Awake() { }
static void Shuffle<T>(IList<T> list) { }
class SaveFile { }
```

✅ Хорошо:

```csharp
[SerializeField] private Button playButton;
private readonly List<Coin> _coins;
private void Awake() { }
private static void Shuffle<T>(IList<T> list) { }
private class SaveFile { }
```

Порядок: атрибуты, затем модификатор доступа, затем `static` / `readonly` / `const` / тип.  
У свойства модификатор обязателен; у аксессора — только если он строже, чем у свойства (`public int Collected { get; private set; }`).

### Обязательно

**Не писать `if` / `foreach` / `while` / `for` без фигурных скобок.**

❌ Плохо:

```csharp
if (body == null) return;
foreach (Coin coin in coins)
    coin.Hide();
```

✅ Хорошо:

```csharp
if (body == null)
{
    return;
}

foreach (Coin coin in coins)
{
    coin.Hide();
}
```

То же для `continue`, `break`, `yield break` и вложенных условий.

### `UnityEngine.Object` и оператор `?.`

У типов, наследующих `UnityEngine.Object` (`MonoBehaviour`, `GameObject`, `ScriptableObject`, `Canvas`, …), «пустота» бывает двух видов:

1. **C# `null`** — ссылки нет.
2. **Destroyed** — native-объект уничтожен, но managed-ссылка ещё жива.

Unity перегружает `==` / `!=`, поэтому `obj == null` учитывает оба случая.  
Оператор `?.` (и `is null`) проверяет **только** C#-ссылку и **обходит** lifetime check Unity.

❌ Плохо:

```csharp
speedLabel?.gameObject.SetActive(riding);
```

✅ Хорошо:

```csharp
if (speedLabel == null)
{
    return;
}

speedLabel.gameObject.SetActive(riding);
```

**Правило:** на `UnityEngine.Object` не использовать `?.`, `??`, `is null` / `is not null` для проверки «жив ли объект». Использовать `== null` / `!= null`.

Для обычных C#-классов и делегатов (`Crashed?.Invoke()`) `?.` допустим.

### Однострочные методы и expression-bodied синтаксис

**Запрет `=>` относится только к методам (функциям).**  
Expression-bodied **свойства** (`public int X => …`) — нормальный и допустимый стиль.

#### Методы

Не писать методы в одну строку через `=>`. Тело — в фигурных скобках.

❌ Плохо:

```csharp
public int NextCost(int level) => baseCost * (level + 1);
```

✅ Хорошо:

```csharp
public int NextCost(int level)
{
    return baseCost * (level + 1);
}
```

Лямбды в `AddListener(() => …)` — это не методы класса, так писать можно.

#### Свойства

`=>` для свойств **разрешён**:

```csharp
public bool IsFinished => distance >= finishDistance;
public float AverageSpeed => time > 0f ? distance / time : 0f;
```

## 7. UI: сцена, редактор, SerializeField

### Запрет имён `Ensure*`

**Не давать методам имена `Ensure…`.** Имя размытое («убедись что…»), скрывает результат и путается с разным смыслом (создать / дозаполнить / поднять сцену).

| Нужно | Имя |
|-------|-----|
| Создать, если ещё нет; успех явно | `TryCreate…` → `bool` (и `out`, если есть что вернуть) |
| Всегда создать на init | `Create…` / `Initialize…` |
| Сцена уже должна быть | не создавать в рантайме |

❌ Плохо: `EnsureHud`, `EnsureFont`.  
✅ Хорошо: `TryCreateMask`, `CreateFont`.

**Legacy:** если в файле ещё остались `Ensure*` — переименовать **при касании файла**, не пачкой «за компанию». Если неочевидно во что — **спросить до правки**.

### Сцена вместо runtime-создания

**Не создавать** в рантайме инфраструктуру и экраны, которые настраиваются один раз в сцене (`EventSystem`, Canvas, кнопки, подписи).

Иерархия UI — в сцене, её ведём в инспекторе. В `Play Mode` экраны уже существуют; код только включает/выключает их и пишет **содержимое** в существующие тексты и кнопки. Не писать editor-скрипт, который при загрузке проекта ищет дыры в сцене и создаёт недостающие объекты.

### Не менять свойства в рантайме без нужды

Инспектор задаёт вид. Код не перетирает его «на всякий случай» при подписке, показе или обновлении.

**Можно в рантайме** — только то, что иначе не выразить:

- текст, который зависит от данных (счёт, дистанция, цена);
- `SetActive` / `interactable` (показ экрана, блокировка кнопок);
- спрайт, заливка или размер, которые **меняются по состоянию** (шкала, прогресс, плашка под длину текста).

**Нельзя в рантайме** — всё, что уже выставлено в сцене и не зависит от текущего кадра:

- alignment, fontSize, color, wrapping, overflow у текста;
- якоря, padding, LayoutElement, LayoutGroup;
- цвет кнопки, если он уже стоит в инспекторе.

❌ Плохо — код сбрасывает выравнивание, которое только что поставили в инспекторе:

```csharp
label.text = title;
label.alignment = TextAnchor.UpperLeft;
label.fontSize = 32;
```

✅ Хорошо — код пишет только содержимое; вид остаётся из сцены:

```csharp
label.text = title;
```

❌ Плохо в `Awake`:

```csharp
if (FindFirstObjectByType<Canvas>() == null)
{
    var go = new GameObject("Canvas");
    go.AddComponent<Canvas>();
}
```

✅ Хорошо:

- Canvas и экраны — объекты на сцене.
- Ссылки проведены в инспекторе.
- Если обязательное поле `null` — `Debug.LogError`, не тихое создание.

**Исключение:** объекты, которых много и которые порождаются данными (монеты вдоль трассы, куски сгенерированной геометрии). Их создаёт код, и `AddComponent` на таком объекте нормален.

### Сцена: редактор, не YAML руками

Иерархию и ссылки правим в **редакторе Unity** или через инструмент, который управляет редактором.

Если такой инструмент **недоступен**:

1. **Сказать пользователю**, что он недоступен — не молча обходить.
2. **Не править** YAML сцен и ассетов вручную (`*.unity`, `*.prefab`, `*.asset`). Это не запасной путь.
3. Можно менять C# и документы. Для сцены — список шагов в инспекторе.

### `[SerializeField]` — без поиска в рантайме

Поле с `[SerializeField]` **проводится в инспекторе**. Не подставлять его через `FindFirstObjectByType`, `FindObjectOfType`, `FindAnyObjectByType` и не использовать `GetComponent` / `GetComponentInChildren` как fallback «если забыли назначить».

❌ Плохо:

```csharp
[SerializeField] private Canvas canvas;

private void Awake()
{
    if (canvas == null)
    {
        canvas = FindFirstObjectByType<Canvas>();
    }
}
```

✅ Хорошо:

- Ссылка назначена в инспекторе.
- Если поле обязательно и `null` — `Debug.LogError` в `Awake`, без скрытого поиска.

`GetComponent` на **том же** GameObject допустим, если поля нет в инспекторе (компонент на том же объекте по договорённости). Для внешних зависимостей — только `[SerializeField]` + проводка.

## 8. Именование функций: одна ответственность

**Не вшивать в имя и тело метода сразу два разных смысла:** *когда* действие допустимо и *что* оно делает.

❌ Плохо:

```csharp
private void TrySaveAfterRunFinished()
{
    if (run == null || !run.IsFinished)
    {
        return;
    }

    repository.Save(CreateRecord(run));
}
```

✅ Хорошо — условие снаружи, метод делает одно:

```csharp
if (run == null || !run.IsFinished)
{
    return;
}

repository.Save(CreateRecord(run));
```

Правило именования:

- имя описывает **одно действие** (`Save`, `ShowRecord`, `StartRun`);
- **не** кодировать в имени триггер (`AfterWin`, `OnRunEnd`, `WhenTimedOut`) — если только весь класс не является явным обработчиком этого события.

## 9. Мёртвый / устаревший код

- Не оставлять неиспользуемые экраны, поля инспектора и ветки «на всякий случай».
- Не копировать логику во UI «чтобы было под рукой» — источник правды один.

## 11. Как обновлять этот файл

При новых договорённостях (архитектура, стиль, запреты, паттерны):

1. Добавить пункт в нужный раздел или новый раздел.
2. Обновить дату в шапке.

Агент должен **предлагать/вносить правки в `CodeRules.md`**, когда пользователь формулирует устойчивое правило («всегда так делаем», «не хочу X»).
